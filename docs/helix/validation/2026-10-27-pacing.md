# Helix pacing validation — 2026-10-27

## Scope

Validated the first Helix 0.2 sender-side packet pacing experiment on Quest 3 with matching desktop/server and APK builds.

The experiment compared the existing unpaced sender against fixed 100 us and fixed 50 us shard spacing. The test workload was a stable VRChat scene to reduce content-driven variance.

## Unpaced baseline

Main streams each sent about 57.9k frames.

- average frame size: about 30.4 KB
- average shards per frame: 22
- average send span: 107–109 us
- maximum send span: 1.79–1.91 ms
- sender queue depth max: 1
- average sender queue delay: 6–7 us
- average inter-frame gap: 11.113 ms

Approximately 99.6% of frames were emitted in less than 0.25 ms, confirming a real UDP microburst pattern.

## Fixed 100 us shard spacing

The mechanism worked mechanically and stretched a typical frame across about 2.20 ms, but runtime behavior was not good enough to keep as the default experiment point.

- average send span: 2.195–2.197 ms
- sender queue depth max: 2
- average queue delay: 7–8 us
- average inter-frame gap remained about 11.11 ms
- repeated IDR requests were observed throughout the session

Decision: do not promote 100 us spacing.

## Fixed 50 us shard spacing

The 50 us setting kept the intended burst smoothing while reducing added sender occupancy and avoiding the obvious 100 us regression.

- stream 0: 69,436 frames, average send span 1.172 ms, max 3.011 ms
- stream 1: 69,430 frames, average send span 1.173 ms, max 4.429 ms
- average shards per frame: 23
- sender queue depth max: 1
- average sender queue delay: 7 us
- average inter-frame gap: 11.112–11.113 ms
- only one >4 ms slow-send outlier on stream 1 and none on stream 0

Some IDR requests still occurred, so this test does not prove that fixed pacing materially reduces end-to-end packet loss. It proves that a 50 us fixed pacer can substantially smooth the sender without creating a persistent queue or materially changing frame cadence.

## Decision

Keep fixed 50 us pacing as the provisional Helix checkpoint.

Do not spend additional headset-test cycles tuning 25/75 us or nearby values now. Revisit pacing only when later packet-loss, FEC, retransmission, or delivery telemetry can show whether further tuning produces a meaningful end-to-end reliability gain.

Next high-impact focus: Helix 0.3 receive-side reordering and deadline-aware packet recovery.
